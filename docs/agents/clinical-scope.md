# 医疗与阶段范围

修改产品文案、问诊相关模型、临床资料或申请后续能力时读取本页及
[Phase3-E资料包](../clinical-validation/phase3-e/README.md)。

## 输出边界

项目服务院内医生的规则学习、计算展示、问诊线索整理及教学复盘目标。
当前输出限于理论说明、规则解释、线索整理和教学提示，医生拥有最终解释权。
禁止自动诊断、自动辨证、处方和治疗决策；不得给出方剂、中药、剂量、疗程或治法。
禁止把运气结构解释为疾病因果、吉凶或治疗建议。

可陈述“资料中存在相关线索”“从传统理论角度存在对应关系，供医生参考”；
不能断言患者属于某证或因某气导致某病。专业传统术语仍受中性解释边界约束。

## 当前授权能力

Phase3-E工程范围为当前五运六气、1900–2100运气年分析、用户明确提交固定北京时间后的
`/yunqi/calculate` 指定时点分析；均是版本化规则的计算与展示。
`/yunqi/inquiry` 仅为C4规划入口，enabled只表示可访问。

当前禁止新增患者搜索/选择、患者档案、问诊创建/记录、观察记录表单、症状采集、
Patient/Inquiry/Observation API、Client、Query Hook、Mock、存储和问诊子路由。
HIS/EMR、身份权限执行、真实问诊、教学页面、专家审核、规则管理、风险预测、推荐及AI
均需后续明确授权，不能从路线图或启用导航推导已上线。

## C4内部只读模型

Patient、Inquiry、Observation、Permission、Audit Context Model仅限
`apps/yunqi-workbench/src/features/inquiry/models` 的内部只读类型边界。
只能由该目录type-only index内部导出，禁止inquiry feature根导出；生产Page/component
不得导入或实例化，不能提升为API DTO、服务端实体或医疗事实。
不得加入通用metadata、角色枚举、生命周期、诊疗或推断字段。

HIS/EMR接入必须通过正式API/Contract，不能扩metadata绕过契约。
Observation专业类别等待专家确认；身份、角色和RBAC等待真实认证与组织模型。
后续建议评估顺序为专家流程验证 → Inquiry Service → OpenAPI Schema → Contracts → Client → React，
该顺序是建议，不是能力已经实现的证据。

## 问诊目标与后续路线

得到独立授权后，问诊采集目标包括主诉、发病时间、就诊时间、寒热、汗、饮食、
二便、睡眠情志、舌象和脉象。目标输出仅为症状标签、六淫线索、八纲单项线索和时气对应提示；
仍禁止自动生成证型、诊断和方药。不得从规则结果反推未录入的舌脉等事实。

Phase1领域、Phase2服务/契约、Phase3工作台、Phase4教学/专家/规则管理是路线目标。
后两项路线不能替代每项能力的单独授权和验收；本次复盘也不启动后续阶段。

## 专家与临床证据

规则实现基线仍待正式专家冻结；API工程冻结和测试PASS不能改变该状态。
是否进入真实临床工作流须经过专家验证和独立Gate。
真实临床事实、独立专家预期答案、身份权限和责任边界先由专家及正式设计确认，
再进入Service/OpenAPI/Contracts/Client/React链路。

E3需要真实专家确认的参考材料；E4需要真实脱敏Demo反馈和前序证据。
缺少材料时保持对应BLOCKED状态，G1–G6不得从空模板自动转PASS。
不能把程序输出填成专家预期，不能虚构审核人、日期、签名、共识或临床结论。
原始输入时间与API规范时间分别记录；患者关联时间应省略并给非识别性原因。
每条反馈绑定会话、任务/示例、完整构建SHA和反馈ID，独立完成情况与理解/认同分开记录。
