## 领域理解

1. **先确定运气年，再确定年干支。**公历日期的年份不一定等于运气年；大寒前仍归上一
   运气年，交节当刻才进入新年。春节和立春不参与这次归属。
2. **年干与年支承担不同映射。**年干决定岁运五行、太过/不及和五音；年支决定司天、
   在泉。1984 甲子是六十甲子索引锚点，不能直接使用历法库的立春年柱替代。
3. **主气顺序与客气顺序不同。**主气第三步为少阳相火、第四步为太阴湿土；客气循环中
   太阴位于少阳之前。客气以司天居第三步定位，第六步必须等于在泉。
4. **六步是实际交节区间。**起点依次为大寒、春分、小满、大暑、秋分、小雪，末端为
   下一年大寒。各区间左闭右开；等宽 UI 阶段不表示实际时长相等。
5. **客主关系必须分层表达。**同一六气、同五行但不同六气、相生/相克方向分别保存。
   少阴君火与少阳相火是不同六气，只有五行相同；传统描述不产生吉凶或诊疗结论。
6. **时间的历法含义来自固定北京时间字段。**UTC+08 不应用历史 DST。
   `epochMilliseconds` 是排序、传输、审计与兼容表示。Service 字符串必须先经唯一
   normalizer 转为 CalendarTime，之后按本地字段判年、判步。
7. **支持的运气年范围不是公历日期首尾。**现行 API 支持 1901–2099 运气年，因此
   2100 年大寒之前仍可归入 2099；1901 年大寒之前则归入不支持的 1900。

## 待决事项与不能扩大解释的结论

**D-01 / R-08：查询范围。**Word 为1900–2100；Phase2-A明确将 Service 限为已有
边界证据的1901–2099，且扩大范围需要适配器证据和契约版本决策。当前实现正确执行
了冻结范围，但两份业务文件尚未统一。若以Word为目标，应明确这是运气年范围，完成
新增范围验证、Contract ID、SemVer及迁移记录；不能直接改旧 snapshot。

**D-02 / R-21：客生主标签。**Word 明确“客生主，相得”，当前规则常量及测试为
“客生主”。历史开发计划因提示词未指定其余方向而选择中性标签，不等于专家正式废止
R-21。若采用Word，应在领域规则层按规则版本/说明/测试/审核状态一起处理，前端不得
偷偷追加“相得”。目前没有把任一文字纳入新的权威标签 oracle。

确认单本身要求确有冲突时由中医科形成书面口径；本轮请求的是采用依据的澄清，
没有将用户未回复视为批准，也没有替专家完成冻结。

**Provider错误分类。**Provider抛错返回503；其返回逆序边界后由Domain抛RangeError
则返回400。旧Phase2-A与专门测试明确保留后者，后续时间规范措辞较概括，因此当前
不列为已确认规则缺陷。若将来统一为依赖失败，应先明确分类，不能在Service复制
Domain的边界规则。

**证据范围。**锁定tyme4ts秒值的全范围工程归属检查，不是独立天文精度证明；项目
来源说明已区分分钟级外部年表与库的秒值。Workbench的人为组合展示fixture不是
真实年份规则答案。原始规格中的正式专家批准、第二历法误差阈值及临床核验仍不能
由本轮自动生成。
