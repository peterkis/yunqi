# 运气通 Windows 0.2.2 · WebView2 内存与唤醒实测

## 测量范围

工作目录为 `D:\Projects\YunQi-rust`，分支为 `rust/native-desktop`，HEAD 为 `7d6ce9b532407322faffb9f51e31455c394dd69d`。开始时核对的 1,091 个项目文件与 0.2.1 上轮工作树记录逐文件一致。0.2.1 含尚未提交的 Rust 改造，单独检出这个 HEAD 无法复原测试输入。运行系统为 Windows 11 专业版 build 26300，i7‑1260P，16 个逻辑处理器。通过本次应用的自有浏览器进程确认 WebView2 Runtime 为 158.0.4370.33。

主要 A/B 将同一份原工作台资源、完整字体和原宿主用于普通对照，实验宿主只增加非活跃内存策略。两组各独立启动三次，顺序为对照、LOW、LOW、对照、对照、LOW。各轮使用新的 WebView2 用户目录，核对可执行文件 SHA、一个主窗口、窗口几何、浏览器进程角色和命令行。普通内存采样使用 Release，应用启动参数无远程调试，未连接 Playwright 或打开 DevTools。独立交互诊断使用环回 CDP，指标单独记录。测试保留系统的文件缓存及后台任务；本机有一个先于本轮开始、持续使用约一个逻辑核的进程。检查器在实际光标移动、窗口状态不符或关闭核验失败时保留失败记录。样本少，结果适用范围为这台机器与相应工作负载。

`PrivateWorkingSetSize` 表示各自有进程当时驻留的私有物理页，私有提交量 `PrivateUsage` 也包含未驻留的分配。分组总工作集会重复加总共享页，GPU 进程工作集也不能据此换算成显存。以下内存均为 MiB，1 MiB = 1,048,576 字节。[Win32 内存计数器](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2)

## 唤醒后能否继续工作

在每组单独一次的真实 WebView2 交互诊断中，先答完前三题，真实收边 75 秒，期间不向页面轮询 CDP。以系统鼠标进入感应条前的时刻为共同起点。两组使用同一份工作台和固定操作顺序。

| 从鼠标进入开始 | 普通 | LOW |
| --- | ---: | ---: |
| HWND 到达展开尺寸 | 4.71 ms | 4.40 ms |
| 页面执行完两次 requestAnimationFrame 回调 | 20.19 ms | 28.58 ms |
| 实际点第 4 题后，第 5 题出现在 DOM | 371.09 ms | 385.48 ms |

双 rAF 是渲染调度代理，不能保证某帧已显示到屏幕。第 5 题指标包括自动化点击和控件原有答题延时。本机这一对 LOW 分别多 8.39 ms 和 14.39 ms；每版一次，无法估计 P95 或慢磁盘上的最大回填成本。两组都保持同一页面身份，继续完成 26 题、显示结果、销毁答卷，再切换 78 像素胶囊与展开。另一次功能探针验证短时收边及最小化后草稿仍可继续。此段使用环回调试，仅作功能与延迟证据。

另用真正的 Windows 最小化做单因素诊断，每组独立启动一次。Win32 `IsIconic` 为真，原生图标化尺寸为 160×28；真实 WebView 内部可能仍报告 `visible` 和 1020 高。75 秒时，普通和 LOW 全树私有工作集为 161.93 与 34.94 MiB，私有提交为 257.12 与 242.12 MiB。从 `SW_RESTORE` 到 400×1020 原生几何分别为 5.78 与 6.07 ms。普通组采样时有并行的编译及测试，因此此组只用于核实优化方向。

## 打开工作台时的内存

为测量展开页面本身，使用同一普通宿主依次载入完整首页、极简空白页和使用字体分片的相同首页，各启动两次。顺序为完整、空白、分片、分片、空白、完整。视口均为默认浮窗 400×1020，此处无需移动指针。以下为两次的中位数。

| 展开状态 | 完整首页 | 空白页 | 字体实验 v2 |
| --- | ---: | ---: | ---: |
| 20 秒，全树私有工作集 | 163.14 | 87.69 | 121.38 |
| 40 秒，全树私有工作集 | 162.26 | 88.61 | 120.64 |
| 40 秒，全树私有提交 | 253.65 | 147.30 | 183.14 |

## 已合并的改动

- `desktop/src-tauri/src/webview_memory.rs` 结合原有 `dock.rs` 的 HWND 状态处理，只在连续贴顶隐入 6 像素或 Windows 窗口最小化 10 秒后向 `ICoreWebView2_19` 请求 LOW。展开、恢复时向同一 WebView 请求 NORMAL。按窗口线程维护 COM 引用，调用前释放临时借用，处理消息重入和旧定时消息，窗口销毁时清理。旧运行时缺少可选接口时沿用普通模式。这个策略是一项异步提示，10 秒是提交请求的等待期，实际驻留量各阶段由运行时和 Windows 决定。[WebView2 内存接口](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2_19)
- `apps/yunqi-workbench/src/providers/desktop-host.ts` 与两处时钟 hook 共享查询策略。原生感应条的 CSS 已把正文隐藏，文档仍报告 `visible`。在 Windows 桌面视口高度不超过 8 像素时暂停分钟轮询，回到活动视口只为超过 60 秒的活动时钟查询补取。更新不重建页面、不触发量表重置。78 像素胶囊继续遵循现有查询规则。最小化时本机网页仍可能报告 `visible` 且高 1020，此项前端优化只对窄条生效，宿主 LOW 同时覆盖真正的最小化。
- 修复 Windows 测量工具只依赖父 PID 可能误收其他进程的问题。一次功能检查曾将一个早于测试宿主数小时启动的其他进程计入退出等待。现在比对子进程和父进程创建时间、快照与句柄身份。原始失败记录保留。对已有测量的进程角色复核、退出检查和创建时间回归分别留有记录。

## 时钟、字体和 Rust 核心

使用构建后的两份工作台 JS、模拟的 Tauri 通道、实际 Release Rust probe 和同一受控浏览器时钟分别访问当下页及出生页。四组测试分别经过三分钟 400×6、展开、正常分钟、78 像素视口。原版收边每页新增 3 次调用，新版均为 0。新版展开即补 1 次，再过 1 分钟新增 1 次。短时间反复收边由独立 QueryObserver 回归覆盖。这里的时间为虚拟时间，请求均由 Rust 返回成功。

现行设计要求完整中文字体。原版首页可见干支标题使用宋体，正文和图例使用黑体。单独去掉 `document.fonts.load(...)` 只会延迟宋体读取，并可能造成首帧字体替换。字体仅在隔离候选中试验，保持完整原件用于回退，另提供覆盖 1,119 个常用码点的同源小字库。互斥字符范围的第二版在当前、出生、量表三个入口各读取 708,960 B 字体，原版各读取 18,695,156 B，读取量减少约 96.2%。含“龘”的混排验证回退到了原字库，访问生僻字后两份字库可能同时载入。第一版字符范围重叠，会在显式预载时继续加载整份宋体，已单列淘汰。字体包大小、字体解压大小及进程私有工作集是不同的量。

400×994、1× 的 Chromium 156 固定场景中，第二版的首页、量表和稀有字混排截图逐像素一致。出生页 397,600 个像素中有 6,244 个变化，最大单通道差 2/255；原基线自身复跑差 0。三页的可见文字和已采集的控件几何相同。两个完整字体及许可文件保留于正式发布。有关字体范围匹配见 [CSS Fonts 4](https://www.w3.org/TR/css-fonts-4/#composite-fonts)。

Rust 的节气索引有 1,836 个按需填充的槽；农历生日按 1900–2100 年设 201 个惰性年份入口；量表定义为 7,791 B，首次使用才解析；经典为静态常量。上轮 Windows Release 分配探针显示，遍历全部年份并释放输出后保留的活跃堆为 163,359 B，第二遍净增加 0 B。本轮未修改规则或历法实现，以上堆探针为 0.2.1 历史依据；本轮重新核对源码，并直接测得了宿主驻留。[0.2.1 审查记录](rust-review-2026-11-27.md)
