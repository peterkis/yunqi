## 3. 核心概念分离

系统必须区分以下概念，不能使用同一个“年份”字段混用。

### 3.1 公历年 `civilYear`

输入时刻在 `Asia/Shanghai` 下对应的公历年份。

### 3.2 运气年 `yunQiYear`

按照配置的运气年边界确定的年份标签。

MVP 默认：

```text
当年大寒精确时刻之前：yunQiYear = civilYear - 1
当年大寒精确时刻及之后：yunQiYear = civilYear
```

### 3.3 运气年干支 `yunQiGanzhi`

由 `yunQiYear` 的数值直接计算，基准：

```text
1984 = 甲子
```

系统不得直接采用以下结果作为 `yunQiGanzhi`：

- 农历库返回的春节换年年柱；
- 八字库返回的立春换年年柱；
- 输入日期公历年份未经年界判断的干支。

### 3.4 六气周期 `sixQiCycle`

起于该运气年的大寒精确时刻，止于下一年大寒精确时刻，采用左闭右开：

```text
[大寒(year), 大寒(year + 1))
```

### 3.5 岁运先天 / 后天

“太过先天、不及后天”是二期单独建模的岁运到达概念。

它不得改变：

- `yunQiYear`；
- 六气六步边界；
- 司天、在泉所属年份。

## 4. 时间和历法规范

### CAL-001 默认时区

系统必须使用：

```text
Asia/Shanghai
```

所有外部输入必须转换为绝对时刻，再按该时区判断公历年和节气边界。

### CAL-002 节气必须使用精确交节时刻

必须通过 `CalendarProvider` 获取以下节气的精确时刻：

- 大寒；
- 春分；
- 小满；
- 大暑；
- 秋分；
- 小雪；
- 下一年大寒。

不得使用：

```text
1月20日、3月21日、5月21日……
```

这类固定日期只能出现在说明文字中作为大致月份，不得参与计算。

### CAL-003 运气年边界

伪代码：

```ts
function resolveYunQiYear(input: Instant): number {
  const civilYear = yearOf(input, "Asia/Shanghai");
  const daHan = getSolarTermInstant(civilYear, "大寒");
  return input >= daHan ? civilYear : civilYear - 1;
}
```

### CAL-004 运气年干支

```ts
stemIndex = mod(yunQiYear - 4, 10)
branchIndex = mod(yunQiYear - 4, 12)
```

输出：

```ts
stem = STEMS[stemIndex]
branch = BRANCHES[branchIndex]
ganzhi = stem + branch
```

必须使用数学正模，兼容早于公元 4 年的扩展情形；MVP 推荐仅开放 1900—2100 年。

### CAL-005 区间规范

所有时间区间统一使用：

```text
[start, end)
```

例如：

```text
输入时刻 == 春分交节时刻
```

必须归入“二之气”，不能仍归“初之气”。

### CAL-006 时间存储

建议：

- 服务内部：UTC `Instant`；
- 数据库存储：带时区时间戳；
- API：ISO-8601；
- 页面展示：Asia/Shanghai；
- 输出结果同时记录历法提供方和版本。

| 年支 | 司天 | 在泉 |
|---|---|---|
| 子、午 | 少阴君火 | 阳明燥金 |

| 巳、亥 | 厥阴风木 | 少阳相火 |

### LQ-ST-002 位置不变量

必须满足：

```text
三之气客气 == 司天
终之气客气 == 在泉
```

任一条件不满足，规则引擎必须抛出内部一致性错误。

### LQ-ST-003 半年总领与分步值分离

数据模型可以同时记录：

- 司天：传统理论中总领上半年；
- 在泉：传统理论中总领下半年；
- 三之气客气：具体分步位置；
- 终之气客气：具体分步位置。

界面不得把“司天只等于三之气”简化成它仅影响第三步；也不得将“总领”解释为现代气象因果。

### LQ-ZQ-001 主气固定顺序

| 步 | 名称 | 主气 |
|---:|---|---|
| 1 | 初之气 | 厥阴风木 |

| 6 | 终之气 | 太阳寒水 |

主气顺序与客气三阴三阳顺序不同。实现中必须建立两个独立常量，不得共用一个数组。

### LQ-ZQ-002 六步节气边界

| 步 | 开始 | 结束 |
|---:|---|---|
| 初之气 | 当年大寒 | 当年春分 |
| 二之气 | 当年春分 | 当年小满 |
| 三之气 | 当年小满 | 当年大暑 |
| 四之气 | 当年大暑 | 当年秋分 |
| 五之气 | 当年秋分 | 当年小雪 |
| 终之气 | 当年小雪 | 下一年大寒 |

### LQ-ZQ-003 当前步骤算法

```ts
steps.find(step => input >= step.start && input < step.end)
```

必须恰好匹配一步；匹配 0 步或多步均视为内部错误。

### LQ-ZQ-004 节气数据完整性

必须验证：

```text
大寒 < 春分 < 小满 < 大暑 < 秋分 < 小雪 < 次年大寒
```

若不满足，必须停止计算，不得静默纠正。

```ts
const sitianIndex = GUEST_ORDER.indexOf(sitian);
```

## 10. 客主加临关系

### REL-001 计算输入

每一步分别取：

```text
主气五行
客气五行
```

### REL-002 关系分类

| 条件 | 代码 | 中文显示 |
|---|---|---|
| 主客同五行 | `SAME` | 同气，相得 |
| 主气生客气 | `HOST_GENERATES_GUEST` | 主生客，相得 |
| 客气生主气 | `GUEST_GENERATES_HOST` | 客生主，相得 |
| 主气克客气 | `HOST_CONTROLS_GUEST` | 主胜客，逆 |
| 客气克主气 | `GUEST_CONTROLS_HOST` | 客胜主，从 |

### REL-003 解释边界

上述关系只是规则关系，不等同于：

- 气候必然异常；
- 患者一定发病；
- 某证候已经成立；
- 某治疗原则必然适用。

### REL-004 待专家确认项

“相得 / 不相得”“顺 / 逆 / 从”的不同教材表述可能存在细分。MVP 可按上表展示，但必须由中医专家审核后冻结。

## 11. 端到端算法

```text
输入日期时间
↓
转换为绝对时刻
↓
以 Asia/Shanghai 获得 civilYear
↓
获取 civilYear 大寒精确时刻
↓
确定 yunQiYear
↓
按 yunQiYear 数值计算年干支
↓
由年干计算岁运、太过/不及、五音
↓
由年支计算司天、在泉
↓
获取 yunQiYear 的六个节气边界及次年大寒
↓
生成六步主气
↓
以司天定位三之气并轮转生成六步客气
↓
计算每步客主关系
↓
以 [start,end) 找到当前步骤
↓
输出规则版本、历法提供方、结构化结果和安全提示
```

### 11.1 推荐函数

```ts
resolveYunQiYear(input, calendarProvider)
ganzhiOfNumericYear(yunQiYear)
calculateSuiYun(stem)
calculateSitianZaiquan(branch)
buildSixQiBoundaries(yunQiYear, calendarProvider)
calculateGuestQi(branch)
calculateHostGuestRelation(hostQi, guestQi)
calculateYunQi(input, options)
```

### 11.2 禁止的实现方式

```ts
// 禁止：仅按公历年份直接计算
const ganzhi = ganzhiOfNumericYear(date.getFullYear());

// 禁止：固定日期
const daHan = new Date(`${year}-01-20T00:00:00+08:00`);

// 禁止：复用春节或立春年柱
const ganzhi = lunarDate.getYearGanzhi();
```

```ts

  ganzhi: string;

  suiYun: {
    element: Element;
    state: "太过" | "不及";
```

## 14. 错误处理

| 错误码 | 场景 | 处理 |
|---|---|---|
| `CALENDAR_TERM_NOT_FOUND` | 节气不存在 | 阻断计算 |
| `CALENDAR_TERM_ORDER_INVALID` | 节气次序异常 | 阻断计算 |
| `DATE_OUT_OF_SUPPORTED_RANGE` | 超出支持年份 | 返回明确提示 |
| `YUNQI_GUEST_QI_INVARIANT_BROKEN` | 三之气不等于司天或终之气不等于在泉 | 阻断计算 |
| `YUNQI_STEP_NOT_UNIQUE` | 当前时刻匹配不到唯一一步 | 阻断计算 |
| `YUNQI_RELATION_UNRESOLVED` | 五行关系未解析 | 阻断计算 |
| `RULE_VERSION_NOT_APPROVED` | 使用未审核规则 | 原型可警告，正式环境阻断 |
| `TIMEZONE_NOT_ALLOWED` | 非约定时区直接参与计算 | 转换或拒绝 |

不得以默认值掩盖缺失节气数据。

## 16. 二期规则设计

本章为设计规格，不代表已完成专家确认。

### 16.1 主运

#### WY-ZY-001 五步顺序

```text
木 → 火 → 土 → 金 → 水
```

每步传统长度为七十三日零五刻。

#### WY-ZY-002 传统交司节点

开源实现和常见资料给出以下传统节点：

```text
初运：大寒日起
二运：春分后十三日
三运：芒种后十日
四运：处暑后七日
终运：立冬后四日
```

但具体时辰随年支组变化：

| 年支组 | 初运 | 二运 | 三运 | 四运 | 终运 |
|---|---|---|---|---|---|
| 子、辰、申 | 寅初初刻 | 寅正一刻 | 卯初二刻 | 卯正三刻 | 辰初四刻 |
| 丑、巳、酉 | 巳初初刻 | 巳正一刻 | 午初二刻 | 午正三刻 | 未初四刻 |
| 寅、午、戌 | 申初初刻 | 申正一刻 | 酉初二刻 | 酉正三刻 | 戌初四刻 |
| 卯、未、亥 | 亥初初刻 | 亥正一刻 | 子初二刻 | 子正三刻 | 丑初四刻 |

实现要求：

1. 先保留传统时间标签；
2. 不得未经确认直接换算成现代时分秒；
3. 需要专家确认采用何种古代时刻换算模型；
4. 需要决定是否使用历法节气精确时刻加日数，还是传统定时标签。

#### WY-ZY-003 主运太少

主运的木火土金水固定，但太少排法需结合当年中运定角。

社区实现存在算法，但正式实现前必须形成 60 年主运太少人工确认表。

### 16.2 客运

#### WY-KY-001 初运

客运第一步等于当年岁运。

#### WY-KY-002 相生与太少交替

从第一步起：

```text
下一客运五行 = 当前五行所生
下一客运太少 = 当前太少相反
```

示例：甲年土运太过：

```text
太土 → 少金 → 太水 → 少木 → 太火
```

#### WY-KY-003 主客运并列

每个五运步骤应同时输出：

- 主运五行与太少；
- 客运五行与太少；
- 主客五行关系；
- 传统交司时间。

### 16.3 岁运先天 / 后天

设计为独立字段：

```ts
interface SuiYunArrival {
  mode: "先天" | "后天";
  offsetDays: -13 | 13;
  referenceTerm: "大寒";
  instant?: string;
}
```

初步规则：

```text
太过：先天十三日
不及：后天十三日
```

待确认：

- “十三日”采用自然日还是传统日刻；
- 是否叠加大寒精确时刻；
- 如何处理平气；
- 该字段仅作理论展示还是参与其他规则。

## 19. 已知歧义与项目决策

### 19.1 大寒、立春、春节年界

不同历法或术数库可能分别使用：

- 大寒；
- 立春；
- 农历春节。

本项目 MVP 决策：

```text
五运六气运气年：大寒精确时刻
```

立春可保留为实验配置，但不同边界计算结果必须明确标记，不得混合缓存。

### 19.2 年干支来源

项目决策：

```text
先确定 yunQiYear，再由数值年推干支。
```

这是为了保证一月大寒前仍使用上一运气年的干支和司天在泉。

### 19.3 精确时刻还是整日

项目决策：

```text
计算使用精确时刻，页面可以同时显示日期。
```

### 19.4 固定日期近似

项目决策：

```text
禁止参与计算。
```

### 19.5 实际气候和物候

五运六气规则结果是传统理论结构，不是现代气象观测。页面应允许后续增加“实际物候记录”，但二者必须分栏显示。

### 19.6 医疗解释

规则引擎只回答：

```text
是什么、处于哪一步、规则关系如何
```

不回答：

```text
患者得了什么病、应如何处方
```

## 22. 最终实施结论

MVP 的核心原则为：

```text
大寒精确年界
→ 运气年数值推干支
→ 年干定岁运
→ 年支定司天在泉
→ 固定主气
→ 司天居三之气排客气
→ 精确节气时刻划分六步
→ 五行生克计算客主关系
→ 结构化输出
→ 模板解释
→ 医生参考，禁止自动诊疗
```

在规则专家审核完成前，系统页面必须显示：

```text
当前规则版本尚处于原型审核阶段，结果仅供规则校验和教学研究。
```
